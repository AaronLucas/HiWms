## 1. 为什么需要这份文档

海外仓/集运商/3PL 运营商评估一个 WMS 供应商时，**不会看你的代码架构，只会看
你能不能解决他今天正在头疼的具体问题**：货主的货会不会混、账对不对得上、
现场工人好不好用、系统会不会崩。这份文档要回答三件事：

1. 这类客户到底关心哪些能力维度，用他们自己的行话怎么说
2. 4 份报告里的技术发现，哪些如果原文照搬给客户看，会造成误解或者根本没人
   看得懂
3. 这类客户在第一轮技术评估对话里最常问的"红线问题"，本项目现在的真实答案
   是什么（包括不利的答案）

## 3. 工程黑话 vs 业务语言的鸿沟：哪些结论不能原文照搬

以下是 4 份报告里**如果原文甩给客户会造成误解、或者客户根本看不懂**的表达方式，
以及应该怎么翻译。核心原则：**客户关心后果，不关心机制**。

| 报告原文黑话 | 问题 | 应该怎么说 |
|---|---|---|
| "L0-L4 业务能力成熟度标尺"、"没有任何业务能力越过 L2" | 客户不知道 L2 是什么意思，可能误以为"L2 = 60% 完成度"这种线性进度条 | "目前所有功能都还停留在'系统内部有这个逻辑'的阶段，还没有一个功能做到'一个真实的人能坐下来、点点鼠标或扫扫码把活干完'" |
| "RLS（行级安全）/`tenant_id`/`service_role`/RPC" | 纯数据库实现术语，客户会觉得在被"炫技"或被绕晕，容易产生"listen 不懂=心虚"的负面联想 | 直接说"我们有没有做到货主之间数据物理隔离"，不解释怎么做到的，除非客户自己是技术背景会追问 |
| "测试覆盖率 11.45%（Statements）/CI 不设阈值/`describe.skipIf`" | 客户如果只看到"11.45%"这个数字，容易直接当成"及格线的对立面"来砍价或一票否决，但也可能被更差的销售话术美化成"高级优化后的精简测试"——两个方向的误读都危险 | "这套代码目前还没有经过系统性的自动化验证，相当于一辆还没做过碰撞测试的车——不代表一定不安全，但代表现在没人能保证" |
| "CRITICAL/HIGH/P1/P2 严重度分级" | 客户不熟悉工程分级习惯，容易把 HIGH 当成"还好，没到最高级"，反而低估风险 | 用后果描述代替等级词："这个问题一旦触发，后果是……"，而不是说"这是一个 HIGH 级问题" |
| "静默失败"、"`SKIPPED_NOT_PENDING`"、"返回看起来正常的字符串" | 这类描述如果原文照搬，会显得"这系统连自己出错了都不知道"，比问题本身更吓人，容易在第一轮对话直接触发否决 | 如实说"这条链路我们自己还没验证过它在真实使用下是活的还是死的，这是我们目前最优先要搞清楚的事，而不是回避" |
| "六边形架构/45 个端口/9 个 UseCase（5:1 抽象比）" | 纯工程审美自我评价，对客户没有任何决策价值，甚至可能暴露"过度工程化、没有对应真实用户"的负面信号 | 不主动提及。如果客户自己问"你们代码写得规范吗"，回答"底层工程规范做得比较扎实，这也是我们现在能相对快速响应真实需求的原因"，不展开细节 |
| "ADR-016/ADR-017 编号冲突"、"双仓库 Issue/addendum 协同流程" | 纯内部治理细节，客户听了只会觉得"连自己内部流程都没理顺" | 完全不提，这类内容不应该出现在任何客户对话材料里 |
| "owner/tenant 语义分裂"、"Cross-Dock D-Core Phase 4 已被 DBA 主动冻结" | 客户听不懂"语义分裂"是什么意思；"主动冻结"这种说法如果照搬，容易被理解成"项目出了大问题在紧急止血" | "货主账目独立管理这块能力，我们判断还需要先跟真实客户核实清楚具体业务场景再往下做，目前主动放在了后面，避免做错方向返工" |
| "9 个独立诊断维度交叉验证"、"ICE 优先级评分" | 这是团队内部方法论工具，客户不关心你怎么做的自我诊断，只关心结论 | 只呈现结论，不解释诊断方法论，除非客户主动问"你们怎么知道自己现在处于这个阶段的" |
| "0 用户时指标也能全绿"、"反馈回路已完全闭合在系统内部" | 这是团队自我批评的语言，对客户说会显得在说"我们自己骗自己"，容易被过度解读 | 转译为正面且诚实的说法："我们过去几个月的精力更多投在了打好底层地基上，现在需要真实客户的实际使用来验证这些设计对不对，这正是我们想和您聊的原因" |

## 4. 红线问题（Deal-Breaker Questions）与如实答案

以下是海外仓/集运商/3PL 决策者在**第一轮技术评估对话**里几乎必问的问题，按
"一旦答不好就可能直接结束对话"的红线程度排列。每题给出基于既有 4 份报告的
如实答案——**包括不利的答案**。

### 红线问题 1："你们现在有没有真实仓库/真实客户在用这套系统？"

**如实答案**：目前 0 个真实客户、0 个生产部署、0 个真实用户。团队规模 1 人，
项目开发约 2 个月，目前处于系统内部建设阶段，还没有任何一个真实仓库使用过。
（产品诊断 §0）

### 红线问题 2："如果我现在签约，多久能真正上线用起来？"

**如实答案**：现在没有可信的时间线可以给。目前没有部署环境、没有 Docker/CI-CD
自动化部署流程，也没有任何一个用户界面——现场作业员和仓库管理者都无法通过
界面操作系统，只有后端服务接口存在。任何"上线"都需要从搭建界面和部署链路
开始，实际周期需要看具体需求范围才能评估，现在给出任何具体周期都不负责任。
（健康诊断 §6.5；产品诊断 §0）

### 红线问题 3："我的货主的货/账会不会跟别的货主混、串？"

**如实答案**：数据库层面的多租户隔离设计是本项目相对最扎实的部分（第三方评估
在这一项打了较高分）。但**应用层目前存在 2 个真实的、当前代码就能复现的严重
安全问题尚未修复**：一是系统对"内部管理员账号"和"平台超级管理员"的判断逻辑
写错了，理论上可能导致平台全部租户的数据被任意读取和篡改，包括跨租户重置
别人的登录密码；二是新创建的货位容器记录目前会漏写货主归属信息，可能被其他
货主看到甚至改动。这两个问题在解决之前，**我们不建议、也不会让任何真实货主
数据进入这套系统**。（健康诊断 §1.1/§1.2）

### 红线问题 4："系统会不会出现库存对不上、数据丢失的情况？"

**如实答案**：负责手持终端/扫码枪与服务端之间数据同步的核心链路（拣货、上架、
盘点、打包、异常处理这几个环节），已经用一次真实的端到端联调测试证实——
**目前完全不通**：设备登录本身没问题，但登录之后的任何操作请求都会被拒绝，
数据根本到不了记账那一步，也不会有任何报错提示现场人员。根因已精确定位到
一行代码级别的权限判断错误，且影响范围比最初预判的更大——不只是这几个作业
环节，是设备登录成功之后的几乎所有操作。这是我们当前排在第一位、必须先修复
才能在有真实客户数据进入前解决的事情。（PDA 链路 E2E 验证报告）

### 红线问题 5："你们怎么帮我给货主自动核算仓储费/操作费、自动出账单？"

**如实答案**：这块能力目前基本是空的。数据库层面设计了计费相关的表，但从项目
一开始到现在几十次数据库迭代里，这部分设计几乎没有跟着业务往前推进，负责
计算仓储费的核心代码目前在整个系统里没有被任何地方实际调用——也就是说现在
系统还不能帮您自动给货主算账、出账单。行业里这恰恰是最值钱的一块能力，我们
判断这也是接下来投入的优先方向之一，但现在不能说"已经有"。（健康诊断 §0.6/§5；
竞品对标 §3/§6）

### 红线问题 6："现场分拣员/仓管员能不能直接用扫码枪/手持终端操作，好不好上手？"

**如实答案**：目前完全没有可以给人用的界面——无论是电脑端还是手持终端，
前端代码是 0 行。所有现有功能目前只是后端的数据接口，需要开发出对应的操作
界面之后，现场人员才能真正用起来。（产品诊断 §0）

### 红线问题 7："危险品、需要温控的货物，你们能不能管？"

**如实答案**：数据库层面已经设计了危险品分级、温湿度分级等合规主数据结构，
这块设计相对完整，但目前**没有任何一个实际功能入口在使用这套数据**——也就是
说这些规则目前存在于数据库里，但操作层面还用不上，也没有经过真实业务场景的
验证。如果您现在就有危险品/温控品的强需求，这块能力还不能现货交付。
（健康诊断 §3.2）

### 红线问题 8："谁能登录系统、谁能操作什么，能不能自己管理账号？"

**如实答案**：目前这块能力是空白的——仓库经理没有办法自己给新来的拣货员开一个
账号。这是我们跨团队复核后新发现的一个关键阻塞项：即便前面提到的操作界面
做出来了，如果账号权限管理不先补上，现场也没有人能真正登录进去用。这一项
现在排在优先解决的位置。（健康诊断 §5；Council 裁决 决策4）

### 红线问题 9："你们的系统安全吗？会不会被黑？"

**如实答案**：目前已知至少 2 个严重级别、当前代码可复现的跨租户安全问题
尚未修复（见红线问题 3），另外还发现：负责设备登录换取访问令牌的接口没有做
任何频率限制，理论上可能被反复尝试破解；还有一处逻辑漏洞，普通租户用户
在正常操作下就可能触发服务器程序崩溃。这些问题目前都记录在案，尚未全部
修复，我们不会在修复前让这套系统对接真实业务数据。（健康诊断 §1）

### 红线问题 10："我的订单量涨起来了，系统扛得住吗？"

**如实答案**：现在没有事实依据能回答这个问题——目前真实订单量是 0，系统从未
在真实业务负载下运行过。（产品诊断 §0）

### 红线问题 11："能不能对接我现在用的 Shopee/Amazon/ERP/快递公司系统？"

**如实答案**：目前没有任何一个外部系统的实际对接实现或验证案例，这是完全
空白的能力项，不能现货承诺。（产品诊断 §0；健康诊断 §5）

### 红线问题 12："你们做这个多久了，团队多大？"

**如实答案**：项目启动约 2 个月，目前是 1 人团队独立开发。（产品诊断 §0）

## 5. 使用建议（写给对话执行者，不是给客户看的部分）

1. **主动坦白优先于被动被问出来**：红线问题 1、2、3、4、5、9、10、12 建议在
   对话早期主动、简短地说明，而不是等客户问到才承认——3PL 决策者习惯性会做
   背调、也见过太多"讲得很满后来兑现不了"的供应商，主动坦白反而是差异化。
2. **能诚实展示的真实强项**：多租户隔离的数据库设计深度、危险品/温控合规
   主数据的结构完整性、对 3PL"货权与库位解耦"这类真实行业问题的理解深度
   （竞品对标 §4：这被独立第三方认为是本项目"最该学 Extensiv 计费引擎打法"
   之外、少数有真实差异化潜力的方向）——这些可以正常谈，但每次都要清楚
   区分"这是设计层面的思路"还是"这是已经跑通验证过的能力"，不要混用。
3. **不要主动谈的内容**：第 3 节列出的全部工程黑话原文、内部方法论、ADR 编号
   冲突、双仓库协同流程细节——这些对客户决策没有帮助，只会制造噪音或误解。
4. **这份文档的有效期**：本文档基于 2026-09-05 的诊断报告快照。健康诊断 §1
   列出的 2 个 CRITICAL 漏洞、已证实失效的核心同步链路，以及**全仓库范围内
   是否还有同款权限校验错误尚待排查**这三件事一旦有新进展（修复/排查完成/
   证伪），本文档第 2、4 节及"范围性风险提示"对应条目需要同步更新，不能
   长期沿用未刷新的答案对外沟通。
